# «ЗАЛЁТ» — онлайн-игра про кейсы. Дизайн

Дата: 2026-11-10. Источник требований: `PROMPT.md`.

## 1. Что строим и зачем

Браузерная онлайн-игра для компании друзей (ПК + телефоны): открытие кейсов, апгрейды, контракты,
батлы. Валюта только виртуальная («монеты»), без доната/вывода/обмена. Интерфейс на русском.

Критерии успеха:
- выглядит как дорогой кейс-сайт (тёмный премиум, стекло, неон по редкости), 60 fps на телефоне;
- все денежные операции считает сервер, результат любого дропа можно перепроверить (provably fair);
- за вечер у каждого много попыток, в компании из 3–4 человек кто-то «залетает»
  (симуляция вечера: до 10 000 доходит 30–50 %, до 100 000 — не меньше 5 %);
- вся экономика крутится в одном файле `src/config/economy.ts`.

Название игры — своё («ЗАЛЁТ»), без чужих брендов, логотипов, названий скинов и графики.

## 3. Архитектура

Рассмотренные варианты серверной логики:

1. **Postgres-функции (RPC, PL/pgSQL) — выбрано.** Атомарные транзакции «из коробки», установка =
   вставить один SQL-файл в SQL Editor, ноль холодных стартов. Минус: логика ролла существует дважды
   (TS — для симуляции/проверки честности, SQL — на сервере). Лечится parity-тестами TS ↔ SQL.
2. Edge Functions (Deno/TS, общий код с клиентом). Один язык, но деплой через CLI, холодные старты,
   транзакции через несколько round-trip'ов — хрупко для денег.
3. Firebase RTDB + Cloud Functions. Запасной вариант из ТЗ; Functions требуют платного тарифа.

```
src/config/economy.ts ─┐ (числа)
src/config/cases.ts ───┤ (контент: названия, темы)
                       ▼
            src/shared/catalog.ts  ── строит каталог: веса (ppb), цены с коэффициентом k
              │            │
   клиент (показ, проверка) │
                            ▼
              scripts/gen-sql.ts → supabase/seed.sql → таблицы cfg_* в Postgres
                                                           │
   React-клиент ── supabase.rpc(...) ──► public.* (SECURITY DEFINER) ──► game.* (внутренние)
        ▲                                                  │
        └──── Realtime (postgres_changes → «пинок») + polling `sync` как страховка
```

- **Клиент**: Vite + React + TypeScript, Zustand, Framer Motion, Howler (звуки синтезируются в рантайме
  в WAV), Tailwind v4, lucide-react, HashRouter (работает на GitHub Pages без rewrites).
- **Сервер**: Supabase Postgres. Клиент обращается только к RPC. Таблицы под RLS: публичные —
  только `select`, приватные — без политик вовсе; `insert/update/delete` у клиента нет нигде.
  Внутренние функции живут в схеме `game`, которая наружу не выставлена.
- **Расширения не нужны**: HMAC-SHA256 реализован на чистом PL/pgSQL поверх встроенного `sha256`.
- **Вход**: анонимная сессия Supabase + ник и PIN. Ник свободен → создаётся профиль; занят → нужен
  PIN (так можно зайти с другого устройства). Сессий на профиль может быть несколько.
- **Синхронизация**: один RPC `sync` возвращает состояние игрока, новые сообщения чата, новые записи
  ленты, список батлов, дождь, коинфлипы. Realtime только ускоряет (любое событие → `sync`),
  polling страхует, если Realtime недоступен.
- **Отложенные зачисления**: выигрыш батла/коинфлипа лежит в `pending_credits` с `available_at` =
  конец анимации и попадает на баланс при следующем обращении. Сервер отдаёт раунды батла по мере
  наступления их времени — подсмотреть исход заранее нельзя.

### Деньги и честность

- Все суммы — целые «копейки» (1 монета = 100), `bigint`. Вся арифметика целочисленная, чтобы TS и SQL
  давали бит-в-бит одинаковый результат.
- `hex = HMAC_SHA256(key = server_seed, msg = client_seed + ":" + nonce)`.
  - `n0` = первые 13 hex (52 бита) → `ticket = n0 mod 1 000 000 000` → исход (предмет + фаза);
  - `n1` = следующие 8 hex → износ `fi = n1 mod 10000` (float = fi / 10000);
  - `n2` = следующие 8 hex → StatTrak-аналог, если `n2 mod 10000 < 1000`;
  - `n3` = следующие 8 hex → служебные розыгрыши (ничьи и т. п.).
- Цена экземпляра: `base × (12000 − 4·fi) / 10000` (износ даёт от +20 % до −20 %, в среднем ×1.0),
  затем ×1.5 за счётчик. Фазы ножей/перчаток — отдельные строки таблицы исходов со своей ценой.
- У игрока активная пара сидов: хеш server seed виден заранее, client seed меняется игроком,
  nonce растёт на каждый ролл. «Сменить сид» раскрывает старый server seed — после этого любой
  ролл с ним перепроверяется на странице «Честность» (WebCrypto в браузере).
- У батла и коинфлипа свой server seed: хеш виден в лобби, сид раскрывается после окончания.

### Экономика

- Таблица редкостей и модификаторов — из ТЗ. Для каждого кейса считается точное матожидание сырой
  стоимости (с учётом счётчика и фаз) и коэффициент `k = RTP / E[raw]`.
- `npm run simulate`: 1 000 000 открытий каждого кейса через ту же функцию исхода, что в игре.
  Главный ролл берётся стратифицированной выборкой (иначе при хвостах ×600 шум на 1 млн ≈ 1 % и
  проверка «±1 %» была бы лотереей); печатает факт. RTP, шансы ≥x2/x10/x50/x100, падает при
  отклонении > 1 %. Плюс симуляция вечера (2 часа, бонусы, слив → второй шанс).
- Приток бесплатной валюты: старт 1 000, бесплатный кейс раз в 10 мин (с жирным хвостом), дейлик со
  стриком, второй шанс раз в 15 мин при сливе, награды батл-пасса и заданий, дождь, промокоды.

## 5. Модель данных (Postgres)

Публичные (RLS: `select` всем): `profiles` (ник, аватар, баланс, статистика, прогресс БП),
`feed` (лента событий), `chat`, `battles` (без результатов), `coinflips`, `rain`.

Приватные (RLS без политик): `sessions` (auth uid → профиль), `secrets` (PIN-хеш), `seeds`,
`rolls` (журнал честности), `items` (инвентарь), `battle_results`, `pending_credits`,
`counters` (метрики для заданий), `claims` (задания/достижения/уровни БП), `promo_uses`,
`recipe_uses`, `rain_joins`, конфиг `cfg_kv`, `cfg_cases`, `cfg_outcomes`, `cfg_items`.

Публичные RPC: `login`, `logout`, `sync`, `get_inventory`, `open_case`, `sell_items`, `sell_below`,
`upgrade`, `contract`, `battle_create/join/add_bot/leave`, `get_battle`, `coinflip_create/join/cancel`,
`claim` (задание/достижение/уровень БП), `bonus_free_case`, `bonus_daily`, `bonus_second_chance`,
`promo_redeem`, `rain_join`, `chat_send`, `leaderboard`, `get_profile`, `set_avatar`,
`fair_state`, `fair_rotate`, `fair_set_client_seed`, `fair_rolls`.

## 6. Ошибки и границы

- Любая ошибка RPC — исключение с русским текстом; клиент показывает тост и пересинхронизируется.
- Гонки: строка профиля блокируется `for update` в начале каждой денежной функции.
- Лимиты: инвентарь ≤ 3 000 предметов, чат ≤ 200 символов и не чаще раза в секунду,
  PIN — блокировка после 5 неверных попыток.
- Версия конфига (хеш каталога) сверяется клиентом: при расхождении — баннер «перезалей seed.sql».

## 7. Тестирование

- Vitest: рулетка и расчёт шансов, цены/модификаторы, k-масштабирование, апгрейдер, контракты, батлы.
- Parity-тесты TS ↔ SQL на локальном Postgres (одинаковые сид/nonce → одинаковый дроп).
- Интеграционные тесты RPC на локальном Postgres (деньги, права, гонки, батлы, бонусы).
- Playwright на локальном стеке (Postgres + dev-шлюз, имитирующий API Supabase): открыть кейс,
  продать, апгрейд, контракт, батл с ботом — на 375 и 1440 px со скриншотами, без ошибок в консоли;
  батл и чат с двух вкладок под разными никами.
